# DIOS Luna 제품 요구사항 문서(PRD)

문서 상태: Draft v1.0  
작성일: 2026-08-02  
제품명: DIOS Luna  
제품 유형: 로컬 우선 Electron 기반 문서·메모리·AI 운영 콘솔

## 1. 제품 정의

DIOS Luna는 비개발자가 여러 폴더에 흩어진 문서, 메모리, 스킬, 워크플로, API 연동과 AI 운영 기록을 한곳에서 이해하고 관리하도록 돕는 로컬 우선 운영 콘솔이다.

Luna는 개발자 용어를 별도 사전으로 외우게 하는 대신, 사용자가 실제 작업을 하다가 막히는 순간 해당 화면과 작업에 맞는 설명·예시·다음 행동을 보여주는 문맥형 운영 안내자 역할을 한다.

Luna가 지향하는 핵심 경험은 “파일을 보여주는 뷰어”가 아니라 다음의 반복 가능한 운영 루프다.

```text
폴더 연결 → 스캔 → 분류/중복 제거 → 검토 → 검색/관계 탐색 → 기록/승인 → 다시 스캔
```

사용자는 현재 상태, 문제가 있는 항목, 다음에 해야 할 일을 한 화면에서 이해할 수 있어야 한다. 사용자가 `md`, `Skill`, `Workflow`, `Memory`, `API`, `Phase`, `Task`, `운영지침`을 처음 접해도 각 개념의 의미와 사용 순서를 알 수 있어야 한다.

## 2. 배경과 문제

현재 DIOS에는 스캐너, SQLite 저장소, 문서·그래프·실험·의사결정·AI 리소스·Human Gate 도메인과 여러 React 화면이 존재한다. 그러나 실제 사용을 위해서는 기능 간 연결과 운영 안전성이 더 필요하다.

현재 확인된 대표 문제는 다음과 같다.

- 새 화면 셸에서 기존 Dashboard, Graph, Timeline, AI 리소스, 실험, 의사결정, Human Gate 기능에 접근할 수 없다.
- 스캔 경로와 메모리·스킬 경로가 코드에 하드코딩되어 있다.
- Windows 경로 구분자 때문에 메모리와 스킬 분류가 깨질 수 있다.
- 스캔 폴더 설정이 앱 재시작 후 복원되지 않는다.
- 설정 저장이 실제 저장이 아니라 콘솔 출력에 머물러 있다.
- 트리 검색, 비상 정지, 사용량 초기화, 감사 로그가 실제 운영 계약을 완성하지 못했다.
- Markdown/HTML 콘텐츠가 정제 없이 Electron 렌더러에 삽입될 수 있다.
- 현재 테스트는 핵심 일부 로직을 검증하지만 렌더러·IPC·실제 DB 스키마 통합을 충분히 검증하지 않는다.

## 3. 비전

Luna는 사용자가 폴더 구조와 내부 구현을 이해하지 않아도 문서 운영을 수행하게 한다.

사용자가 Luna를 열었을 때 바로 알 수 있어야 하는 세 가지는 다음과 같다.

1. 지금 어떤 데이터가 연결되어 있는가?
2. 어떤 항목이 새로 생겼거나 문제가 있는가?
3. 다음에 검토하거나 승인해야 할 것은 무엇인가?

## 4. 목표 사용자와 핵심 작업

### 4.1 주요 사용자

- 개인 개발자: 여러 프로젝트의 문서와 AI 스킬·메모리를 관리한다.
- AI 운영자: 에이전트 정의, 자동화 기록, 비용과 승인 상태를 확인한다.
- 프로젝트 리드: 결정 사항, 실험 상태, 문서 관계를 추적한다.
- 비개발자 바이브코딩 사용자: AI에게 요청하고 결과를 검토하면서 프로젝트 구조와 운영 방법을 배운다.

### 4.2 핵심 작업

#### 작업 A: 폴더를 연결하고 최신 상태를 확인한다

사용자는 폴더를 선택하거나 경로를 입력하고, 지원 파일·제외 규칙·마지막 스캔 결과를 확인한다.

#### 작업 B: 필요한 문서를 빠르게 찾는다

사용자는 파일명, 본문, 태그, 상태, 카테고리, 수정일로 검색하고 결과를 미리 본다.

#### 작업 C: 파일의 의미와 관계를 이해한다

문서, 프로젝트, 결정, 실험, AI 리소스, Human Gate가 어떤 관계인지 그래프 또는 관계 패널로 확인한다.

#### 작업 D: 안전하게 기록하고 승인한다

비용 변경, 실험 승인, 자동화 확대 등 위험한 작업은 Human Gate를 거치고, 모든 결과는 감사 로그에 남는다.

#### 작업 E: 문제가 생기면 중단하고 복구한다

비상 정지는 실제 실행 중인 작업을 중단하고, 중단 원인·시각·영향 범위를 표시한다.

#### 작업 F: 생소한 개념을 이해한다

사용자는 운영지침, Phase, Task, 서버, API, Agent 등의 항목을 클릭해 쉬운 설명, 실제 프로젝트에서의 사용 위치, 현재 상태, 다음 행동을 확인한다.

#### 작업 G: API 연동 현황을 확인한다

사용자는 어떤 서비스가 연결되어 있고, 어디에 사용되며, 어떤 목적과 권한을 가지고 있고, 마지막 연결 확인이 언제였는지 확인한다. API 키는 로컬 SQLite에 저장할 수 있으며 화면에서는 기본 마스킹하고 사용자가 직접 공개할 수 있다.

#### 작업 H: Phase와 Task를 따라간다

사용자는 로드맵을 Phase 단위로 보고, 현재 Phase의 목표와 Task를 확인하며, 각 Task에 연결된 문서·운영지침·완료 증거를 한곳에서 본다.

## 5. 제품 원칙

1. 로컬 우선: 원본 파일은 사용자가 선택한 로컬 경로에 남기고, 앱은 필요한 인덱스와 메타데이터만 저장한다.
2. 시각적 우선: 텍스트 목록만 제공하지 않고 상태 배지, 진행률, 카테고리, 다음 행동을 함께 보여준다.
3. 한 화면 한 목적: 탐색, 검토, 설정, 승인 화면의 목적을 섞지 않는다.
4. 안전한 기본값: 읽기는 자동화할 수 있지만 삭제·외부 전송·비용 변경·고위험 실행은 확인과 감사가 필요하다.
5. 설명 가능한 자동화: 자동 분류나 추천은 근거와 신뢰도를 보여준다.
6. 중단 가능성: 모든 장시간 작업은 시작, 진행률, 취소, 중단 결과를 제공한다.
7. 단일 진실 공급원: 화면 상태와 도메인 상태를 별도 임시 객체로 흩어지게 하지 않는다.
8. 용어보다 의미 우선: 화면의 기본 라벨은 쉬운 한국어로 쓰고 원래 영어 용어를 괄호로 병기한다.
9. 사용자를 가르치되 대신 결정하지 않는다: Luna는 설명·추천·정리를 제공하고 중요한 결정은 사용자에게 남긴다.

## 6. 제품 범위

### 6.1 MVP 범위

- 폴더 추가·삭제·복원·스캔
- Markdown, HTML, JSON, YAML 파일 인덱싱
- Windows/macOS 경로 정규화
- 파일명·본문·태그·카테고리 검색
- 문서 미리보기와 안전한 Markdown 렌더링
- 스캔 상태, 오류, 제외 규칙, 마지막 변경 시각 표시
- Dashboard, Tree, Memory, Skill, Agent 화면의 공통 탐색 모델
- 설정 영속화
- 기본 감사 로그와 실제 Human Gate 상태 표시
- 동작하는 비상 정지와 실행 취소
- 작업 중 필요한 문맥형 설명과 운영 안내
- API·서비스 연동 보관함
- Phase·Task·운영지침·로드맵의 시각적 연결
- 유지보수·서버 운영 상태와 대응 지침
- Agent 활용 가이드와 Agent별 사용 범위

### 6.2 후속 범위

- 문서 관계 그래프
- AI 리소스 비용·사용량 이력
- 실험 상태 전이와 의사결정 레저
- 스킬 비교·번역·관계 분석
- 에이전트 실행 기록과 추천
- 선택적 로컬 AI 요약 및 분류

### 6.3 비범위

- Luna가 원본 파일을 사용자 동의 없이 수정하거나 삭제하는 기능
- 기본값으로 문서 전체를 외부 AI 서비스에 업로드하는 기능
- 완전한 팀 협업·다중 사용자 권한 시스템
- 검증되지 않은 자동 실행을 “승인됨”으로 표시하는 기능

## 7. 정보 구조와 화면

### 7.1 상위 내비게이션

- 홈: 상태 요약, 최근 변경, 검토 대기, 다음 행동
- 소스: 연결 폴더, 스캔 실행, 스캔 이력
- 탐색: 트리, 검색 결과, 문서 미리보기
- 메모리: patterns/projects/sessions/failures/success
- 스킬: 스킬 목록, 태그, 비교, 관계
- 에이전트: 에이전트 정의, 상태, 실행 기록
- 계획: 로드맵, Phase, Task, 완료율
- 운영지침: 운영 규칙, 체크리스트, 실행 순서
- 연동: API와 서비스 연결 현황, 권한, 연결 상태
- 운영센터: 운영지침, 유지보수, 서버 상태, Agent 활용법
- 고급 운영: AI 리소스, 실험, 의사결정, Human Gate, 감사 로그
- 설정: 경로, 제외 규칙, 저장소, 보안, 알림

### 7.2 공통 화면 구성

모든 주요 화면은 다음 순서를 따른다.

1. 화면 목적과 현재 범위
2. 상태 요약 카드
3. 검색·필터·정렬
4. 결과 목록 또는 시각화
5. 선택 항목의 상세 패널
6. 사용자가 다음에 할 수 있는 명확한 행동

## 8. 기능 요구사항

### FR-01 연결 폴더 관리

- 사용자는 폴더 선택 대화상자 또는 경로 입력으로 폴더를 추가할 수 있어야 한다.
- 저장된 폴더는 앱 재시작 후 복원되어야 한다.
- 중복 경로는 한 번만 저장해야 한다.
- 존재하지 않는 경로는 오류 상태와 복구 방법을 보여줘야 한다.

수용 기준: 폴더를 추가한 뒤 앱을 재시작해도 목록이 유지되고, 폴더 삭제 시 해당 폴더의 결과가 화면에서 제거된다.

### FR-02 스캔 엔진

- 지원 확장자, 제외 패턴, 최대 파일 크기를 설정할 수 있어야 한다.
- 스캔은 `queued → running → completed|failed|cancelled` 상태를 가져야 한다.
- 각 스캔은 시작 시각, 종료 시각, 파일 수, 오류 수, 취소 여부를 기록해야 한다.
- 동일 파일은 해시로 변경 여부를 판단해야 한다.
- 경로 구분자는 내부 계약에서 `/`로 정규화해야 한다.

수용 기준: Windows 경로에서 메모리·스킬 분류가 정상 동작하고, 스캔 취소 시 추가 파일이 결과에 반영되지 않는다.

### FR-03 검색과 탐색

- 파일명, 상대 경로, 본문, frontmatter 메타데이터를 검색해야 한다.
- 검색 결과는 검색어, 카테고리, 파일 형식, 수정일, 소스 폴더로 필터링할 수 있어야 한다.
- 트리 검색 입력은 실제 결과를 필터링해야 한다.
- 결과 선택 시 상세 내용과 원본 경로를 표시해야 한다.

### FR-04 안전한 콘텐츠 미리보기

- Markdown은 허용된 태그만 렌더링하고 스크립트·이벤트 핸들러·위험한 URL을 제거해야 한다.
- HTML은 기본적으로 소스 코드로 보여주고, 미리보기는 격리된 샌드박스에서만 허용한다.
- 원본 파일의 앞부분과 전체 보기 사이를 구분한다.

### FR-05 설정

- 스캔 폴더, 제외 규칙, 자동 스캔 간격, 기본 화면, 테마, 데이터 저장 위치를 저장해야 한다.
- 저장 성공은 실제 영속화 확인 후에만 표시해야 한다.
- 설정 버전을 두어 향후 마이그레이션이 가능해야 한다.

### FR-06 비용과 AI 리소스

- AI 리소스별 월 한도, 현재 사용량, 상태, 사용 이력을 보여줘야 한다.
- 한도 수정 시 양수 검증과 변경 감사 로그를 남겨야 한다.
- 월간 리셋은 현재 월 집계만 초기화하고 과거 이력은 보존해야 한다.

### FR-07 Human Gate와 감사 로그

- 위험 작업은 `PENDING_APPROVAL` 상태에서 실제 실행되지 않아야 한다.
- 승인·거부는 한 번만 가능해야 한다.
- 원본 요청과 해결 기록은 연결되어야 한다.
- `audit_log` 스키마는 앱 초기화 시 반드시 생성되어야 한다.
- 감사 기록은 수정·삭제할 수 없어야 한다.

### FR-08 비상 정지

- 사용자는 확인 또는 즉시 중단으로 실행 중인 작업을 멈출 수 있어야 한다.
- 취소는 타이머와 AbortController를 모두 정리해야 한다.
- 중단 후에는 시스템이 `STOPPED` 상태로 남고, 재개는 명시적인 사용자 행동이어야 한다.
- 중단된 스캔·자동화·외부 호출은 재개되지 않아야 한다.

### FR-09 문맥형 설명과 운영 안내

- 사용자가 Phase, Task, 운영지침, 서버, API, Agent를 선택하면 현재 맥락에 맞는 설명을 보여줘야 한다.
- 설명은 “무엇인가”, “현재 프로젝트에서 어디에 쓰이는가”, “지금 상태는 어떤가”, “다음에 무엇을 하는가”를 포함해야 한다.
- 설명은 별도 사전 메뉴가 아니라 관련 화면의 도움말 패널, 상세 패널, 작업 시작 안내로 제공한다.
- 개발자 원어는 필요한 경우에만 한국어 설명과 함께 병기한다.

수용 기준: 사용자가 실제 Task를 수행하는 중 추가 검색 없이 해당 개념의 목적과 다음 행동을 이해할 수 있어야 한다.

### FR-10 API·서비스 연동 보관함

- 사용자는 연결된 서비스의 이름, 제공자, 목적, 사용 위치, 상태, 마지막 확인 시각을 볼 수 있어야 한다.
- 연결별 권한 범위와 데이터가 외부로 전송되는지 표시해야 한다.
- 사용자가 로컬 전용 저장을 승인하면 API 키·토큰을 SQLite에 저장할 수 있다. 백업 파일에 포함될 수 있다는 경고를 표시한다.
- 연결 테스트, 비활성화, 재연결, 삭제를 제공해야 한다.
- 현재 연결되지 않은 API도 “추천 연결” 또는 “연동 예정”으로 구분해 표시할 수 있다.

수용 기준: 사용자는 현재 어떤 서비스가 DIOS에 연결되어 있는지와 어디에 사용되는지 한 화면에서 확인할 수 있어야 한다.

### FR-11 Phase·Task·로드맵

- 로드맵은 `로드맵 → Phase → 목표 → Task → 운영지침 → 완료 증거` 구조를 가져야 한다.
- 현재 Phase와 다음 Phase를 시각적으로 구분해야 한다.
- Task에는 상태, 담당자, 우선순위, 연결 문서, 완료 조건이 있어야 한다.
- 사용자가 기술 용어를 몰라도 Task를 “해야 할 일” 문장으로 읽을 수 있어야 한다.

수용 기준: 사용자는 현재 Phase의 목적과 다음 Task 하나를 즉시 확인할 수 있어야 한다.

### FR-12 운영지침

- 운영지침은 특정 작업을 안전하게 수행하는 순서형 문서다.
- 각 지침은 목적, 사전 조건, 단계, 확인 방법, 실패 시 복구, 완료 증거를 포함해야 한다.
- 지침 실행 여부와 마지막 실행 결과를 기록해야 한다.

수용 기준: 사용자는 지침 하나를 열었을 때 별도 개발 지식 없이 순서대로 실행할 수 있어야 한다.

### FR-14 유지보수·서버 운영 안내

- 프로젝트에 포함된 서버, 데이터베이스, API 서비스, 배포 환경을 목록으로 보여줘야 한다.
- 각 환경은 목적, 위치, 연결 상태, 마지막 확인 시각, 담당 운영지침, 백업 상태를 가져야 한다.
- “시작”, “중지”, “재시작”, “로그 확인”, “백업 확인”, “장애 대응”을 단계별 운영지침으로 연결해야 한다.
- 사용자가 서버를 직접 조작하기 전에 위험도와 예상 영향을 보여줘야 한다.
- Luna는 서버를 임의로 조작하지 않고, 명시된 API·스크립트·사용자 승인 범위 안에서만 동작해야 한다.

수용 기준: 사용자는 서버가 무엇을 위해 존재하는지, 현재 정상인지, 문제가 있을 때 어떤 지침을 따라야 하는지 확인할 수 있어야 한다.

### FR-15 Agent 활용 가이드

- Agent마다 역할, 잘하는 일, 입력해야 할 정보, 결과 형식, 하지 말아야 할 일, 권한 범위를 보여줘야 한다.
- 사용자는 현재 Task에 적합한 Agent를 추천받을 수 있어야 한다.
- Agent 호출 전에는 요청 내용, 대상 파일, 예상 결과, 필요한 승인 여부를 확인해야 한다.
- Agent 결과는 검토 상태와 완료 증거를 남겨야 한다.
- Agent 간 연결은 `계획 → 구현 → 검토 → 테스트 → 승인`처럼 명확한 흐름으로 표현해야 한다.

수용 기준: 사용자는 “이 Agent를 언제 써야 하는가”와 “무엇을 입력해야 하는가”를 화면에서 바로 알 수 있어야 한다.

### FR-13 사용자 번역 레이어

- 사용자는 Skill 또는 문서의 번역을 직접 입력하거나 붙여넣어 저장할 수 있어야 한다.
- 번역은 원본 Markdown 파일과 별도 저장되어야 한다.
- 화면에서 `원문 / 한국어`를 전환할 수 있어야 한다.
- 원본 해시가 변경되면 번역을 삭제하지 않고 `원문 변경됨`으로 표시해야 한다.
- 자동 AI 번역은 기본 실행하지 않고, 향후 사용자가 선택한 문장·문단에만 제공한다.

수용 기준: 사용자가 원본 파일을 수정하지 않고도 Skill을 한글로 읽을 수 있으며, 원본 변경 시 번역 상태를 알 수 있어야 한다.

## 9. 데이터 및 기술 방향

### 9.1 저장소 분리

- SQLite: 설정, 소스 폴더, 스캔 실행, 인덱스 메타데이터, 도메인 기록, 감사 로그
- 원본 파일: 사용자 지정 로컬 경로
- 렌더러 상태: 현재 선택, 필터, 임시 UI 상태만 보유
- 장기 상태: SQLite 또는 버전 관리 가능한 설정 파일에 보유

### 9.2 IPC 계약

모든 IPC는 동일한 응답 구조를 사용한다.

```ts
type Result<T> =
  | { ok: true; data: T; requestId: string }
  | { ok: false; error: { code: string; message: string }; requestId: string }
```

렌더러는 SQLite를 직접 읽지 않고, preload를 통해 검증된 IPC만 사용한다.

### 9.3 장시간 작업

```ts
type JobState = 'queued' | 'running' | 'completed' | 'failed' | 'cancelled'

interface JobProgress {
  jobId: string
  state: JobState
  completed: number
  total: number | null
  message?: string
  error?: string
}
```
